# GenCompass — техническое задание для разработчиков

> Документ объединяет все замечания и решения по продукту: изменения UX формы ввода и пересмотр логики скоринга по научной доказательной базе. Каждый пункт содержит: что сделать, почему, и как проверить, что сделано верно.

---

## 1. Блок «Данные пациента»

### 1.1 Пол и дата рождения — обязательные, влияют на скоринг

**Статус:** оставить обязательными полями, не трогать логику валидации.

**Почему:** пол критичен для X-линкированных заболеваний и части лабораторных красных флагов; возраст дебюта симптомов — один из ключевых предикторов моногенной этиологии (см. раздел 4.1 и файл `gencompass-bibliography.md`, критерий 1).

### 1.2 Дата рождения + Возраст — убрать дублирование

**Текущее состояние:** два раздельных поля ручного ввода — «Дата рождения» и «Возраст».

**Что сделать:** оставить поле «Дата рождения» источником истины. Поле «Возраст» становится **read-only** и вычисляется автоматически на клиенте при изменении даты рождения (полных лет на дату оценки).

**Приёмка:** ввод даты рождения → поле «Возраст» заполняется без участия пользователя; поле недоступно для ручного редактирования.

### 1.3 ФИО, № медкарты, предварительный диагноз — свернуть в collapsed-блок

**Текущее состояние:** «Фамилия», «Имя», «Отчество», «№ медицинской карты» отображаются развёрнуто по умолчанию на верхней части формы.

**Что сделать:** обернуть эти поля в компонент-аккордеон, свёрнутый по умолчанию. В свёрнутом виде показывать заголовок вида «Пациент: [не указан] ▾» или «Пациент: Иванов И.И. ▾», если ФИО уже введено. Разворачивается по клику.

**Почему:** эти поля не влияют на скоринг — чистая идентификация. Клиницист должен видеть чекбоксы клинических признаков как можно раньше на экране.

**Приёмка:** при открытии формы блок ФИО/№ карты свёрнут; поля Пол/Дата рождения/Возраст видны сразу без разворачивания.

### 1.4 Код оценки

**Что сделать:** не показывать поле «Код оценки» на экране ввода вообще (сейчас это read-only с текстом «Присваивается при сохранении» — оно бесполезно на этапе ввода и просто занимает место). Код присваивается на backend при сохранении и показывается только на этапах 2–3 воркфлоу («Результат и обоснование», «Направление»).

## 2. Блок «Данные приёма»

### 2.1 Предварительный диагноз / причина оценки — единственное обязательное поле блока

**Статус:** оставить видимым и обязательным.

**Почему:** нужен как контекст для блока «Что влияет на оценку» (why this score) и для итогового направления к генетику.

### 2.2 Дата оценки — скрыть по умолчанию

**Что сделать:** дефолт — сегодняшняя дата, поле не показывается на экране. Доступ к изменению — через «Показать доп. поля» (см. п. 2.5).

### 2.3 Тип приёма — заменить dropdown на чипы

**Текущее состояние:** select с опциями («Первичный» и т.д.).

**Что сделать:** заменить на кнопки-чипы (2–3 варианта в один клик). Дефолт — «Первичный».

### 2.4 Профиль врача — автозаполнение из localStorage

**Поля:** «Лечащий врач», «Специальность», «Медицинская организация».

**Что сделать:**
1. При первом заполнении любого из трёх полей — после сохранения оценки записать значения в `localStorage` под ключом вида `gencompass_clinician_profile` (JSON: `{ name, specialty, organization }`).
2. При открытии формы «Новая оценка» — если ключ существует, автоматически подставить значения во все три поля.
3. Дать возможность отредактировать профиль (значения остаются обычными полями, просто предзаполненными) — изменение в форме должно обновлять значение в `localStorage` при следующем сохранении.

**Приёмка:** врач вводит данные один раз → при создании следующей оценки поля уже заполнены; изменение поля и сохранение обновляет профиль.

### 2.5 Скрытие административных полей

**Что сделать:** объединить «Дата оценки», «Тип приёма» (если нужно поменять дефолт), «Лечащий врач», «Специальность», «Медицинская организация» под разворачиваемый блок «Показать дополнительные поля приёма», свёрнутый по умолчанию **после того, как профиль врача заполнен** (при первом использовании блок можно показать развёрнутым, чтобы врач мог задать профиль).

**Итоговый порядок экрана для типового повторного пользователя:**
1. Пол + Дата рождения (сворачиваемый блок ФИО рядом, свёрнут)
2. Предварительный диагноз (одна строка)
3. → сразу «Клинические признаки» (чекбоксы)

## 3. Общий принцип разделения полей

Ввести на уровне архитектуры формы чёткое разделение двух слоёв данных, чтобы в будущем не путать, что можно скрывать/автозаполнять, а что нельзя:

| Слой | Поля | Влияет на скоринг | Можно скрывать/автозаполнять |
|---|---|---|---|
| **Клинический** | Пол, дата рождения, все чекбоксы критериев (см. раздел 4) | Да | Нет, только UI-упрощение (чипы вместо dropdown) |
| **Идентификационный** | ФИО, № карты, дата оценки, тип приёма, врач, специальность, организация | Нет | Да — сворачивать, автозаполнять, задавать дефолты |
| **Контекстный** | Предварительный диагноз | Нет (не входит в формулу), но нужен для explainability и направления | Нет — единственное обязательное поле в «Данных приёма» |

## 4. Логика скоринга — научное обоснование и веса критериев

Полная библиография (56 источников, 6-7 на каждый критерий) — в файле `gencompass-bibliography.md`. Здесь — выводы, которые должны напрямую повлиять на реализацию весовой модели.

### 4.1 Критерий 1 — Возраст дебюта симптомов
**Вес:** высокий, обратная зависимость (чем раньше дебют — тем выше балл).
**Обоснование:** ACMG guideline использует возраст дебюта как критерий включения (до 1 года для врождённых аномалий, до 18 лет для ЗПР/ИН). Диагностический выход WES при эпилепсии с дебютом ≤5 лет — 33%, при дебюте >2 лет — падает до 4–14%.

### 4.2 Критерий 2 — Семейный анамнез
**Вес:** высокий, аддитивный.
**Обоснование:** позитивный семейный анамнез статистически увеличивает шансы молекулярного диагноза в 2,1–4,7 раза (OR) в нескольких независимых когортах (ретинальные дистрофии, ХБП).

### 4.3 Критерий 3 — Консангвинность ⚠️ ТРЕБУЕТ ИЗМЕНЕНИЯ ЛОГИКИ

**Текущая проблема:** если консангвинность реализована как самостоятельный аддитивный балл (наравне с остальными критериями) — это не подтверждается данными.

**Что показывают данные:** диагностический выход у консангвинных и неконсангвинных пациентов, направленных на секвенирование, статистически не различается (32,5% vs 30,2%, p=0.63). Более того, 38,4% позитивных находок у консангвинных пациентов не соответствуют аутосомно-рецессивному типу наследования — то есть теоретическое обоснование веса (повышенная гомозиготность → выше вероятность АР-заболевания) на практике работает слабее, чем ожидается.

**Причина несоответствия:** консангвинность хорошо предсказывает *популяционный риск до появления симптомов*, но слабо предсказывает *результат теста у уже симптоматичного пациента*, потому что пациент уже отобран в когорту по другим клиническим признакам (возраст дебюта, дисморфология и т.д.) — это снижает добавочную предсказательную ценность консангвинности саму по себе.

**Что менять в реализации:**

1. **Убрать консангвинность как самостоятельный аддитивный балл** с полноценным весом, равным другим критериям.
2. **Реализовать как модификатор (множитель), а не как отдельное слагаемое** — конкретно: множитель применяется только к баллу критерия «Семейный анамнез» (например, ×1.2–1.3 к баллу семейного анамнеза при позитивной консангвинности; точный коэффициент — предмет отдельного клинического решения, не хардкодить без утверждения).
3. **Логика:** если семейный анамнез = 0 (не отмечен), консангвинность НЕ должна давать существенный самостоятельный вклад в итоговый балл. Если семейный анамнез положителен, консангвинность усиливает его вклад.
4. **В блоке "Что влияет на оценку" (explainability):** формулировка не должна утверждать прямую связь консангвинности с вероятностью диагноза. Корректная формулировка: *«Консангвинность повышает вероятность аутосомно-рецессивного типа наследования при подтверждении генетического диагноза и учитывается в сочетании с семейным анамнезом»* — не *«Консангвинность повышает риск генетического заболевания»*.

**Источник:** Journal of Human Genetics, 2015 (DOI через PubMed/Nature, см. библиографию критерий 3, источник №1); GEC-KO Consanguinity Point of Care Tool (см. источник №3 там же).

**Приёмка:** написать unit-тест на формулу скоринга — кейс «консангвинность = true, семейный анамнез = false» не должен давать значимый прирост балла по сравнению с базовым случаем без консангвинности.

### 4.4 Критерий 4 — Мультисистемность поражения
**Вес:** высокий, аддитивный (количество вовлечённых систем может использоваться как градация, не просто бинарный чекбокс).
**Обоснование:** патогенные варианты выявляются значимо чаще при мультисистемных фенотипах против изолированных сложных фенотипов (64,0% vs 14,3%, p=0.02).

### 4.5 Критерий 5 — Дисморфология
**Вес:** высокий, аддитивный.
**Обоснование:** компьютерные инструменты распознавания дисморфических черт лица достигают AUROC 0.86; диагностический выход при явных дисморфических чертах в сочетании с ЗПР — 62,5% в отдельных когортах.

### 4.6 Критерий 6 — Регресс развития / нейроразвитие
**Вес:** самый высокий среди всех критериев.
**Обоснование:** диагностический выход при регрессе развития — 70–81% в разных когортах — систематически выше, чем при любом другом изолированном клиническом признаке в этой библиографии.

### 4.7 Критерий 7 — Резистентность к лечению
**Вес:** высокий, особенно в комбинации с критерием 6 (регресс) или задержкой развития.
**Обоснование:** резистентность к противосудорожной терапии в сочетании с задержкой развития — диагностический выход до 72,2%; изолированная резистентность без сопутствующих признаков — существенно ниже (диагноз выявлен у 1 из 3 пациентов с изолированной резистентной эпилепсией без задержек в одной из когорт).

**Важно для реализации:** аналогично консангвинности, стоит рассмотреть резистентность к лечению как усилитель других неврологических критериев (регресс, задержка развития), а не полностью независимый аддитивный балл — данные показывают резкое падение диагностической ценности при изолированном присутствии этого признака.

### 4.8 Критерий 8 — Лабораторные красные флаги
**Вес:** средний-высокий, но с оговоркой на транзиторность.
**Обоснование:** лабораторные отклонения (метаболический ацидоз, гипераммониемия, гипогликемия) — надёжный красный флаг при наличии, но их отсутствие НЕ исключает IEM (значения могут быть транзиторными).

**Важно для реализации:** UI и логика не должны трактовать «лабораторные показатели в норме» как отрицательный балл или как основание для снижения итогового скора — это должно быть нейтральным значением («не определено»/«норма на момент теста»), а не «признак отсутствует».
